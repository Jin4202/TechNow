## 관측 — 2026-09-08 자동 런

**고친 것들이 다 들어간 첫 정상 런이다.** 직전 두 번은 표본이 되지 못했다:
09-06 은 조사 커버리지 수정 이전이고, 09-07 은 수동 실행 셋이 그날 피드를 미리
써버려서 후보가 2건뿐이었다 (기사 0건, D-54).

```
수집 150 → 후보 32 → 재채점 15 → 임계통과 6 → 선정 5 → 시도 6 → 발행 4
조사 실패 2건   too-few-sources(출처 2건) · stale-topic(출처 0건)
```

| | 값 | 읽는 법 |
|---|---|---|
| 편당 변동비 | **$0.3318** | fixture 의 $0.1912 와 분모가 다르다 (아래) |
| 월 환산 | **$42.51** | 예산 $40 의 **106%**. 알림 발송됨 |
| 고정비 | $0.0897/일 | 월 $2.69 |
| 변동비 | $1.3274/일 | 이 중 커버 이미지 $0.24 (**18%**) |
| 논문 쿼터 | `paperQuota: 0` | **물지 않았다** — 아래 참조 |

**단가는 설명된다.** $0.3318 = 작성+검증 $0.19(fixture 실측) + 번역 $0.046 +
커버 $0.06 + 조사·장면선택. 이상값이 아니라 **지금 구조의 정상 단가**다.
따라서 비용을 내리려면 구조를 바꿔야 하고, 어디를 바꿀지는 아래 1단계의 결정이다.

**쿼터는 검증되지 않았다.** 임계 통과가 6건뿐이라 상한 5건에 거의 다 들어갔고
막을 여지가 자체가 없었다. 장치가 작동한 것이 아니라 **걸릴 일이 없었던 것**이다.
`paper-quota` 가 선정 로그에 실제로 찍히는 날을 봐야 `8.3` 이 닫힌다.

**`stale-topic` 은 처음으로 실제로 걸렀다** — "압력으로 색이 변하는 발광 결정" 이
한 달 넘은 소식이라 조사 단계에서 잘렸다. D-53 의 오탐 수정 이후 정상 동작이다.

**프로덕션을 수동으로 돌리지 않는다.** 수동 실행은 그날 예약 런의 피드를 뺏는다 —
09-07 발행 0건이 그 결과였다. 검증은 로컬 `daily:live` 로 한다 (DB 를 비우고
시작하므로 프로덕션에 영향이 없다).

## 개발 순서 (2026-09-08 재정리)

**원칙**: 계기를 먼저 고치고, 서로 간섭하는 작업은 떼어 놓는다.
계기(`variableCostUsd`)는 09-07 에 고쳤고 위 관측이 그 첫 결과다.

### 1단계 — 비용 (`8.4` 를 막고 있다)

**측정된 문제**: 4편에 월 $42.51 (106%). 상한 5편을 채우는 날이면 약 $50 이다.
예산 안에 들어가려면 편당 변동비를 $0.332 → **$0.249** 로, 약 25% 낮춰야 한다.

**먼저 사용자 결정이 필요하다.** 25% 를 어디서 뺄지는 기술 선택이 아니라 취향이다:

| 안 | 절감 | 잃는 것 |
|---|---|---|
| A. 커버 모델을 되돌린다 (Ultra → schnell) | 편당 $0.057 (**17%**) | 커버 품질. 사용자가 09-06 에 명시적으로 고른 것을 뒤집는다 |
| B. 예산을 올린다 ($40 → $50) | 0 | 없음. 문제를 문제가 아니라고 다시 정의하는 것이다 |
| C. 토큰을 줄인다 | 미지수 | 없음(성공하면). 다만 **일이 가장 많다** |

**C 를 먼저 시도할 값어치가 있는지가 관건이다.** C 의 후보는 둘:

| 무엇 | 근거 |
|---|---|
| **쿼리 생성 A/B** | 커버리지 측정에서 토픽 제목을 그대로 쓰니 4건 중 3건이 최소 출처를 채웠는데, 실제 런의 전문 쿼리 3개로는 1~2건이었다. 조사 실패 2건은 조사비를 쓰고 버린 것이다 |
| **출력 토큰** | 변동비의 68% 가 출력이다 (D-27). 다만 이건 3단계(프롬프트)와 같은 파일을 건드리므로 **동시에 하지 않는다** |

**곁들여**: 커버 원본 리사이즈. Ultra 는 2752×1536(약 1MB)이고 `upload-cover.ts` 에
리사이즈가 없다. 하루 5장이면 Supabase 무료 1GB 를 약 7개월에 채운다.
**비용이 아니라 용량 문제**라 위 결정과 무관하게 언제든 할 수 있다.

### 2단계 — 공개 (`Phase 7` 마무리)

```
7.1 약관·개인정보  →  7.0 이름·도메인  →  7.0a 인증 콜백·SMTP  →  7.7 게이트 제거
   (지금 가능)        (사용자 결정)        (7.0 에 묶임)          (마지막)
```

**`7.1` 만 다른 전부와 독립이다.** 1단계가 사용자 결정을 기다리는 동안 할 수 있는
유일한 일이라 여기로 올렸다.

### 3단계 — 프롬프트 (⚠️ **한 번에 하나씩**)

작성·검증 프롬프트를 건드리는 작업이 둘이다. **동시에 바꾸면 무엇이 효과인지 모른다** —
D-48 에서 이미 겪었다. 각각 fixture 14건으로 따로 재고, 채택 기준(비용·통과율·
계산 지표)을 각각 통과시킨다.

| 순서 | 무엇 | 비고 |
|---|---|---|
| 1 | **문장 길이** | **갚아야 할 빚이다.** 기준선부터 8/8 편이 대역 밖이고(`sentenceMean` 28.2 vs 18.7~26.0) GROUNDING 절이 +1.56 키웠다. D-48 에서 채택 기준을 어긴 채 남겼다. `words` 는 8/8 대역 안이라 **기사 길이가 아니라 문장 길이** 문제다 |
| 2 | **`8.2` 사건 발생일** | 검증 호출에 필드 하나를 더 받는다 (추가 호출 없음). 임계는 기존 기사 분포를 본 뒤 정한다 — 추측으로 정하면 D-51 오탐을 반복한다 |

### 4단계 — 확장 (`8.4` 도메인 번들)

1단계가 끝난 뒤. 완료 기준은 **두 번째 도메인을 설정만으로 붙이는 것** —
코드를 고쳐야 하면 번들화가 덜 된 것이다.

**비용이 도메인 수만큼 곱해진다.** 지금 실측이 한 분야 월 $42.51 이므로 세 분야면
**월 $128** 이다 (예전 추정 $177 은 계기가 고장난 상태의 값이라 폐기한다).

## Phase 8. 읽는 사람 쪽으로 (2026-09-07 추가)

Phase 7 까지는 "돌아가는가" 였다. 여기부터는 **"읽을 만한가"** 다.
사용자가 지목한 문제는 하나로 모인다 — **지금 기사가 너무 전문적이다.**
대상 독자는 그 분야 바깥에 있으면서 흐름은 따라가고 싶은 사람이다.

### 8.1 — 커버 표기 문구 ✅

`article.coverBadge` 를 `AI` → `AI Generated` 로 바꿨다. `coverNotice` 는 그대로다.
두 언어와 375px 에서 배지 폭을 확인했다.

### 8.2 — 소식의 나이를 엄격하게

**지금은 두 층으로 막고 있다** (D-49, D-51):

```
RSS 항목 날짜   → 30일 필터        → IEEE 2021년 아카이브 3건 차단
출처 페이지 날짜 → 토픽 신선도 필터  → sorbitol 같은 케이스 차단
```

**빠진 것은 "사건이 언제 있었나" 다.** 출처 페이지 날짜는 "그 매체가 언제 썼나"
이지 사건 발생일이 아니다. 여러 매체가 지난 연구를 동시에 다시 다루면 출처가
전부 최신인데 사건은 오래된 상태가 된다 — 지금 구조로는 못 잡는다.

방향 (택일이 아니라 순서):
1. **사건 발생일을 뽑는다.** 검증 단계가 이미 출처 본문을 읽고 있으므로
   그 호출에 "이 연구·발표가 언제 있었나" 를 한 필드 더 받는다. **추가 호출이 없다**
2. 뽑은 날짜를 `articles` 에 남긴다. 지금은 어떤 기사가 얼마나 묵은 사건인지
   사후에 확인할 방법이 없다
3. 임계를 넘으면 발행하지 않는다. 임계값은 config 로, env 로 조정 가능하게

**측정이 먼저다.** 이미 발행한 기사들의 사건 발생일을 뽑아보고 분포를 본 뒤에
임계를 정한다 — 추측으로 정하면 D-51 의 오탐을 반복한다.

### 8.3 — 캐주얼한 토픽

**세 번 시도해서 세 번째에 통했다. 앞의 두 번이 왜 틀렸는지가 이 항목의 내용이다.**

**시도 1 — 정렬 규칙 (D-56, 채택 안 함).** 선정이 총점 내림차순이라 학술적 중요도가
흥미를 구조적으로 이긴다고 봤다. 저장된 점수로 모의해보니 **틀렸다** — 하한을
올리든 `interest` 우선으로 정렬하든 가중치를 주든 상위 5건이 거의 그대로였다.
`interest` 하한 4 에서는 5/5 가 동일했다. 이미 뽑히는 것들이 `interest` 4~5 를
받고 있었기 때문이다.

**시도 2 — 루브릭 앵커 (D-57, 채택 안 함).** 그러면 채점 눈금이 문제라고 봤다.
`interest` 앵커에 일상에 닿는 예시를 넣고 "휴대폰 화면에 도착한 제목으로 판단하라",
"중요도와 흥미는 다르다" 를 명시했다. 같은 피드로 다시 채점하니 `interest` 5 가
3.7% → **7.8% 로 늘었다**. 의도와 반대다. 목록은 오히려 더 전문적이 됐다.

**원인은 채점기가 아니라 후보 풀이었다 (D-57).** 사용자의 표현이 열쇠였다 —
"사실상 논문을 그대로 요약해놓은 기사". 세어보니:

```
입력(필터 통과)  ScienceDaily + phys.org 가 66%   ← 둘 다 논문 보도자료 재게시처
임계 통과        논문 토픽이 81%
상위 5건         5건 중 4건이 논문
```

거기에 `novelty` 앵커가 **"A paper or institutional release made public today"**
를 5점으로 정의하고 있었다. **풀이 논문으로 차 있으면 점수를 어떻게 주물러도
논문이 뽑힌다.** 시도 1·2 가 실패한 이유가 이것이다.

**시도 3 — 논문 쿼터 (D-58, 채택).** 점수를 네 번째로 건드리는 대신 **카운터로
막았다** (CLAUDE.md §2.6 과 같은 결). 채점이 토픽의 종류(`paper` / `event` /
`product` / `trend`)를 함께 판정하고, `selectTopics` 가 하루 상한 안에서 논문을
`maxPapersPerDay`(기본 2) 로 제한한다.

```
상한만 적용   5건 중 논문 4
쿼터 적용     5건 중 논문 2   · 막힌 것 10건   (상한 5건은 그대로 채운다)
```

**쿼터 값 2 는 분포를 본 뒤에 정했다.** 먼저 분류만 넣고 재보니 임계 통과 비논문이
14건(event 8 · trend 6)이라 3자리를 채우기에 충분했다. D-51 에서 임계값을 추측으로
정했다가 오탐을 낸 적이 있어 숫자를 먼저 정하지 않았다.

**남은 것 — 실측.** 09-08 런에서는 `paperQuota: 0` 이었다. 임계 통과가 6건뿐이라
상한 5 건에 거의 다 들어갔고 막을 자리가 없었다. **장치가 작동한 것이 아니라 걸릴
일이 없었던 것**이다. 선정 로그에 `paper-quota` 가 실제로 찍히는 날을 봐야 닫힌다.
분류 자체도 완벽하지 않다 — "Valve 가 심의 거부 후 트레일러를 공개" 가 `paper` 로
분류됐다. `run_topics.topic_kind` 로 오분류 빈도를 확인한다.

### 8.4 — 분야 확장 (도메인 번들)

**사용자 결정 (2026-09-07): 분야별로 나뉘어 보인다.** 테크 / 금융 / 스포츠가
각자 메인 목록과 상한을 갖는다. 한 목록에 섞지 않는다 — 섞으면 "새 단백질 구조"
와 "금리 인하" 중 무엇이 더 중요한지 한 자로 재야 하는데, 그 자가 없다.

**좋은 소식: 파이프라인은 이미 분야 중립적이다.** 발굴 → 채점 → 조사 → 작성 →
검증 → 번역 → 커버 어디에도 "과학" 이라는 전제가 없다. 분야에 묶인 것은 **설정
네 개**뿐이다:

| 파일 | 지금 | 도메인화하면 |
|---|---|---|
| `config/feeds.ts` | 과학·기술 매체 5곳 | 도메인별 피드 목록 |
| `config/source-tiers.ts` | 학술지·연구기관 허용목록 | 도메인별 tier (금융이면 Bloomberg·Reuters·SEC) |
| `docs/RUBRIC.md` | 채점 앵커가 과학 예시 | 도메인별 앵커 |
| `config/categories.ts` | 7종, **DB enum** | 도메인별 카테고리 |

그래서 **"도메인 = 설정 번들"** 로 묶으면 새 분야 추가가 코드 변경이 아니라 설정
추가가 된다. 이것이 이 태스크의 핵심이다.
