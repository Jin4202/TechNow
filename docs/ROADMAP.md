# ROADMAP

`MASTER_PLAN.md` §5를 실행 가능한 형태로 옮기고, 리뷰에서 빠진 것으로 확인된 태스크를 **[추가]** 로 끼워 넣었다.
원래 번호는 유지하고, 추가분은 `1.1a` 같은 접미사를 쓴다.

**규칙**
- 태스크 하나 = 작업 단위 하나. 완료 기준을 실제로 만족시킨 뒤 다음으로.
- 완료하면 여기 체크박스와 아래 "현재 위치"를 갱신한다.
- Phase 완료 조건을 만족하기 전에 다음 Phase로 넘어가지 않는다.
- 사이트는 Phase 7까지 접근 게이트 뒤에 있다.

### 개발 순서 (2026-09-07 재정리)

열려 있는 일이 여러 갈래로 흩어져 있어 의존 관계로 다시 세웠다.
**두 가지 원칙으로 정렬했다** — 계기를 먼저 고치고, 서로 간섭하는 작업은 떼어 놓는다.

#### 0단계 — 관측 (작업이 아니라 대기)

**내일 01:00 PT 자동 런을 본다.** 어제 조사 커버리지(D-53)와 GROUNDING(D-47)을
고쳤는데 그 효과가 실제 런에 어떻게 나오는지 표본이 없다. 볼 것:

- `too-few-sources` 실패가 줄었는가 (D-53 이 종단 21% → 39% 로 올린 효과)
- 편당 단가와 `projectedMonthlyUsd`

**프로덕션을 수동으로 돌리지 않는다.** 수동 실행은 그날 예약 런의 피드를 뺏는다 —
2026-09-07 발행 0건이 그 결과였다. 검증은 로컬 `daily:live` 로 한다 (DB 를 비우고
시작하므로 프로덕션에 영향이 없다).

#### 1단계 — 비용 0 작업 (지금 바로, 서로 독립)

| 순서 | 무엇 | 왜 여기인가 |
|---|---|---|

2번이 1·3번보다 중요하다. **틀린 계기로 재면서 최적화하면 엉뚱한 곳을 고친다.**

#### 2단계 — 비용 (`8.4` 를 막고 있다)

0단계 관측을 반영해서 판단한다. 지금 월 약 $59 vs 예산 $40.

- **쿼리 생성 재검토** — 커버리지 측정에서 토픽 제목을 그대로 쓰니 4건 중 3건이
  최소 출처를 채웠는데, 실제 런의 전문 쿼리 3개로는 1~2건이었다. A/B 로 가른다
- **커버 원본 리사이즈** — Ultra 는 2752×1536(약 1MB)이고 `upload-cover.ts` 에
  리사이즈가 없다. 하루 5장이면 Supabase 무료 1GB 를 약 7개월에 채운다

**이 단계가 끝나야 `8.4` 를 켤 수 있다.** 도메인 3개면 월 $177 이다.

#### 3단계 — 프롬프트 (⚠️ **한 번에 하나씩**)

작성·검증 프롬프트를 건드리는 작업이 셋이다. **동시에 바꾸면 무엇이 효과인지 모른다** —
D-48 에서 이미 겪었다. 각각 fixture 14건으로 따로 재고, 채택 기준(비용·통과율·
계산 지표)을 각각 통과시킨다.

| 순서 | 무엇 | 비고 |
|---|---|---|
| 1 | **문장 길이** | **갚아야 할 빚이다.** 기준선부터 8/8 편이 대역 밖이고(`sentenceMean` 28.2 vs 18.7~26.0) GROUNDING 절이 +1.56 키웠다. D-48 에서 채택 기준을 어긴 채 남겼다. `words` 는 8/8 대역 안이라 **기사 길이가 아니라 문장 길이** 문제다 |
| 2 | **`8.3` 채택** | 1단계 모의로 규칙을 고른 뒤 실제 런에서 확인. `interest` 앵커 교체는 정렬 규칙과 **따로** 실험한다 |
| 3 | **`8.2` 사건 발생일** | 검증 호출에 필드 하나를 더 받는다 (추가 호출 없음). 임계는 기존 기사 분포를 본 뒤 정한다 — 추측으로 정하면 D-51 오탐을 반복한다 |

#### 4단계 — 공개 (`Phase 7` 마무리)

```
7.1 약관·개인정보  →  7.0 이름·도메인  →  7.0a 인증 콜백·SMTP  →  7.7 게이트 제거
   (지금 가능)        (사용자 결정)        (7.0 에 묶임)          (마지막)
```

**`7.1` 만 다른 전부와 독립이다.** 언제 끼워 넣어도 되고, 앞 단계가 막히면
여기를 하면 된다.

#### 5단계 — 확장 (`8.4` 도메인 번들)

2단계(비용)가 끝난 뒤. 완료 기준은 **두 번째 도메인을 설정만으로 붙이는 것** —
코드를 고쳐야 하면 번들화가 덜 된 것이다.

| 8.3 | **캐주얼한 토픽을 고르게 한다** | 저장된 점수로 재정렬을 모의해 상위 5건이 바뀌는 것을 보이고, 규칙을 바꾼 뒤 실제 런에서 확인 |
| 8.4 | **분야 확장 구조 (도메인 번들)** | 테크 외 분야 하나를 설정 추가만으로 붙일 수 있음. 파이프라인 코드 변경 없음 |

### 8.1 — 커버 표기 문구

`article.coverBadge` 를 `AI` → `AI Generated` 로. 카드 배지가 길어지므로 폭을
확인한다 (375px 포함). `coverNotice` 는 그대로 둔다.

### 8.2 — 소식의 나이를 엄격하게

**지금은 두 층으로 막고 있다** (D-49, D-51):

```
RSS 항목 날짜   → 30일 필터        → IEEE 2021년 아카이브 3건 차단
출처 페이지 날짜 → 토픽 신선도 필터  → sorbitol 같은 케이스 차단
```

**빠진 것은 "사건이 언제 있었나" 다.** 출처 페이지 날짜는 "그 매체가 언제 썼나"
이지 사건 발생일이 아니다. 여러 매체가 지난 연구를 동시에 다시 다루면 출처가
전부 최신인데 사건은 오래된 상태가 된다 — 지금 구조로는 못 잡는다.

방향 (택일이 아니라 순서):
1. **사건 발생일을 뽑는다.** 검증 단계가 이미 출처 본문을 읽고 있으므로
   그 호출에 "이 연구·발표가 언제 있었나" 를 한 필드 더 받는다. **추가 호출이 없다**
2. 뽑은 날짜를 `articles` 에 남긴다. 지금은 어떤 기사가 얼마나 묵은 사건인지
   사후에 확인할 방법이 없다
3. 임계를 넘으면 발행하지 않는다. 임계값은 config 로, env 로 조정 가능하게

**측정이 먼저다.** 이미 발행한 기사들의 사건 발생일을 뽑아보고 분포를 본 뒤에
임계를 정한다 — 추측으로 정하면 D-51 의 오탐을 반복한다.

### 8.3 — 캐주얼한 토픽

**루브릭 문제가 아니라 정렬 문제다.** `interest` 축은 이미 "과학·기술에 관심은
있지만 전문가는 아닌 독자" 를 정확히 겨냥한다 (`docs/RUBRIC.md` 축 3).
문제는 선정이 **총점 내림차순**이라는 것이다:

```
novelty 5 / impact 4 / interest 3  → 총점 12  ← 뽑힌다 (전문적)
novelty 3 / impact 3 / interest 5  → 총점 11  ← 밀린다 (읽기 좋다)
```

실측 축 평균이 novelty 3.04 / impact 2.34 / **interest 2.99** 로 interest 가
하한(3)에 붙어 있다. **학술적 중요도가 독자 흥미를 구조적으로 이긴다.**

**돈을 쓰기 전에 모의한다.** `run_topics` 에 토픽별 세 축 점수와 근거가 남아 있다.
저장된 점수로 정렬 규칙만 바꿔 상위 5건이 어떻게 달라지는지 보면 된다 — **LLM
호출이 없으므로 비용 0.** 후보 규칙:

- `interest` 하한만 4 로 (축별 비대칭 하한)
- 총점 대신 `interest` 우선 정렬, 동점에서 총점
- 가중 총점 (`interest × 2`)

**모의 결과를 사람이 보고 고른다.** 어느 쪽이 "읽고 싶은 목록" 인지는 점수가
아니라 제목을 보고 판단할 일이다.

곁들여 볼 것: 지금 `interest` 앵커의 예시가 전부 연구 결과다 (대기 신호 검출,
양자 소자, 단백질 구조). **일상에 닿는 예시가 없다** — 앵커를 바꾸면 채점 자체가
달라질 수 있다. 정렬 규칙과 따로 실험한다.

### 8.4 — 분야 확장 (도메인 번들)

**사용자 결정 (2026-09-07): 분야별로 나뉘어 보인다.** 테크 / 금융 / 스포츠가
각자 메인 목록과 상한을 갖는다. 한 목록에 섞지 않는다 — 섞으면 "새 단백질 구조"
와 "금리 인하" 중 무엇이 더 중요한지 한 자로 재야 하는데, 그 자가 없다.

**좋은 소식: 파이프라인은 이미 분야 중립적이다.** 발굴 → 채점 → 조사 → 작성 →
검증 → 번역 → 커버 어디에도 "과학" 이라는 전제가 없다. 분야에 묶인 것은 **설정
네 개**뿐이다:

| 파일 | 지금 | 도메인화하면 |
|---|---|---|
| `config/feeds.ts` | 과학·기술 매체 5곳 | 도메인별 피드 목록 |
| `config/source-tiers.ts` | 학술지·연구기관 허용목록 | 도메인별 tier (금융이면 Bloomberg·Reuters·SEC) |
| `docs/RUBRIC.md` | 채점 앵커가 과학 예시 | 도메인별 앵커 |
| `config/categories.ts` | 7종, **DB enum** | 도메인별 카테고리 |

그래서 **"도메인 = 설정 번들"** 로 묶으면 새 분야 추가가 코드 변경이 아니라 설정
추가가 된다. 이것이 이 태스크의 핵심이다.

**하위 태스크**

| # | 무엇 | 비고 |
|---|---|---|
| 8.4a | `config/domains/` 로 네 설정을 번들화. 테크를 첫 번째 도메인으로 이관 | **동작이 바뀌면 안 된다.** 기존 517개 테스트가 그대로 통과해야 한다 |
| 8.4b | `articles.domain` 컬럼 + `category` enum 을 확장 가능한 형태로 | enum 은 값 추가마다 마이그레이션이다. 텍스트 + 참조 테이블로 바꿀지 판단 |
| 8.4c | 파이프라인이 도메인을 순회. 상한·예산을 도메인별로 | `run_daily` 가 도메인 목록을 돌린다. `pipeline_runs` 에 도메인 기록 |
| 8.4d | 라우팅과 UI — 도메인별 메인 목록 | `/[locale]/[domain]` 형태. 아카이브·카테고리 필터도 도메인 안으로 |
| 8.4e | 두 번째 도메인을 설정만으로 추가해 검증 | **이것이 8.4 의 완료 기준이다.** 코드를 고쳐야 하면 번들화가 덜 된 것이다 |

**⚠️ 비용이 도메인 수만큼 곱해진다.** 지금 테크 한 분야가 상한 5편에 월 약 $59
(토큰 $50 + 이미지 $9, D-52) 다. 세 분야면 **월 $177** 이다. 분야를 늘리기 전에
편당 단가를 내리는 작업(로드맵 "다음 할 일" 1번)이 선행되어야 한다.

**순서 제안**: `8.1` (10분) → `8.3` 모의 (비용 0) → `8.2` → `8.4`.
`8.4` 는 앞의 셋과 독립이지만 가장 크고, 비용 문제가 풀리기 전에는 착수해도
켤 수 없다.
