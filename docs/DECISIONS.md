## 2026-09-04 — 구조 리뷰 확정분 (D-01 ~ D-09)

`ARCHITECTURE.md` 리뷰에서 제기된 9개 항목을 확정했다.

### D-01. `seen_feed_items`에 처리 상태를 둔다

RSS 항목을 **처음 볼 때** `status='pending'`으로 기록한다. 선정 단계(§2.1 6단계)까지 끝나야 `status='processed'`로 갱신한다. 다음 날 런은 `pending` 항목을 다시 후보로 본다. 며칠 지난 `pending`은 폐기한다(기본 3일, config `pendingTtlDays`).

**이유**: 기록 즉시 dedup 처리하면 그룹핑·채점 중 런이 죽었을 때 그 항목들이 영구 유실된다. "실패한 런이 다음 날에 영향을 주면 안 된다"는 §2.1 제약과 충돌했다.
**주의**: 임계값 미달로 **탈락한** 항목도 `processed`다. 탈락은 정상적인 처리 완료이며, 매일 재채점하면 안 된다.

### D-02. 모든 테이블에 RLS, 예외 없음

`MASTER_PLAN` §1.1의 "사용자 소유 테이블에 RLS"를 **"모든 테이블에 RLS, 예외 없음"** 으로 원칙 변경. `articles`, `article_translations`, `article_sources`의 select 정책은 `status='published'`인 행만 허용한다. 파이프라인 쓰기는 anon key가 아닌 service_role key로 수행한다.

**이유**: anon key는 브라우저에 공개된다. `articles`에 RLS가 없으면 draft 기사 전문이 그대로 조회된다.

### D-03. 기사 본문은 JSONB 섹션 배열

`articles.body`를 텍스트에서 JSONB 섹션 배열로 변경한다(소제목, 문단, 참조 출처 번호 목록). `article_translations.body`도 동일 구조. `article_sources`에 `ordinal` 컬럼 추가.
"번역이 구조를 바꾸지 않는다"는 제약을 **섹션 수 비교 + 출처 번호 배열 비교**로 코드화한다.

**이유**: §2.2가 요구하는 섹션별 출처 표기를 담을 자리가 스키마에 없었다.

### D-04. 스케줄은 3개, 발행은 분리 유지

~~Trigger.dev 무료 티어 스케줄 한도는 2개~~ → **실제 한도는 10개.** 기획서의 "두 개" 표현이 틀렸다.
01:00 파이프라인과 07:00 발행을 `wait.until`로 합치지 않고 **별도 스케줄로 유지**한다. 월간 요약까지 3개.

**이유**: 장애 격리. 01:00 런이 걸려 있어도 07:00 발행은 독립적으로 실행되어 `ready` 상태 기사를 내보낸다. 한 런에 6시간 대기를 묶으면 파이프라인 장애가 발행 장애로 번진다.

### D-05. 출처 본문은 `source_texts` 테이블

Storage가 아니라 DB 테이블을 쓴다: `source_texts(article_id | run_id, url, extracted_text, expires_at)`. 매일 런 종료 시 만료분을 삭제하는 정리 태스크를 둔다.

**이유**: 단계 간 전달이 경로가 아니라 쿼리로 끝난다. 트랜잭션·조인·RLS가 그대로 적용되고, Storage 수명주기 관리보다 단순하다. "가져온 페이지를 영구 저장하지 않는다"는 §4 원칙은 `expires_at` + 정리 태스크로 지킨다.

### D-06. 출처 본문을 읽는 모든 단계를 Sonnet으로 통일

작성 / 클레임 추출 / 검증 / 재작성 — 출처 본문을 프롬프트에 싣는 단계는 전부 `claude-sonnet-5`로 통일해 **prompt cache를 공유**한다. 그룹핑·채점은 Haiku, 번역·월간 요약은 Sonnet(출처 본문 미사용)으로 유지한다.
출처 본문 블록은 **모든 단계에서 동일한 순서·동일한 형식으로 프롬프트 앞부분에** 배치한다.

**이유**: 클레임 추출을 Haiku로 두면 20k 토큰짜리 출처 블록을 캐시 없이 매번 새로 보낸다. Sonnet 캐시 읽기가 Haiku 신규 입력보다 싸다. 모델을 섞는 순간 캐시가 쪼개진다.
**변경점**: `MASTER_PLAN` §3의 모델 배정 중 "클레임 추출 = Haiku"를 뒤집는다.

### D-07. 비용을 고정비/변동비로 분리

`pipeline_runs`에 `cost_fixed`(발굴~선정)와 `cost_variable`(조사~이미지, 기사별)를 분리한다.
예산 계산식: **고정비 × 30일 + 변동비 × 기사 수 ≤ 20 USD/월**. 기사당 0.20 USD 목표는 **변동비에만** 적용한다.

**이유**: 발굴·그룹핑·채점은 기사가 0개인 날에도 발생한다. 전체 비용을 기사 수로 나누면 조용한 날의 단가가 왜곡되어 잘못된 최적화를 하게 된다.

**추정 단가는 모델별로 나눈다** (3.16a). 변동비 안에서도 쿼리 생성만 Haiku 다. 전부 Sonnet 단가로 계산하면 그 부분이 12배로 잡혀 예산 경보가 실제보다 일찍 울린다. 반대 방향의 근사 — 클레임 추출(Haiku, D-24)을 Sonnet 단가로 잡는 것 — 은 그대로 둔다. 과대추정은 안전한 쪽이고, 단계를 더 쪼개면 계산이 관리 대상이 된다.

경보는 `projectMonthlyCost` 가 내지만 **아무것도 막지 않는다**. 표본이 하루치라 오탐이 잦고, 실제 상한은 호출 지점의 카운터가 강제한다 (CLAUDE.md §2.6).

### D-08. locale은 URL 경로

`/[locale]/articles/[slug]` 구조(next-intl 표준 패턴). `profiles.locale`은 **언어 없는 경로로 진입했을 때의 리다이렉트 기본값으로만** 사용한다. 두 locale 모두 `hreflang` 태그를 낸다.

**이유**: 계정 설정만으로 콘텐츠 언어를 바꾸면 같은 URL이 두 언어를 서빙하게 되어 SSR 캐싱과 검색 노출이 깨진다.

### D-09. 임계 규칙 표기 통일

"어느 축도 2 이하가 아님"을 **"모든 축이 3 이상"** 으로 문서·코드 전반에서 통일한다. 규칙 전체는 `총점 ≥ 10 && min(axis) ≥ 3`.

**이유**: 부정형 이중 표현이 구현 시 off-by-one을 유발한다.

## 2026-09-04 — Phase 0 실행 중 확정 (D-10 ~ D-14)

### D-10. 패키지 매니저는 pnpm

로컬에 이미 pnpm 10.34.3이 있고 `create-next-app --use-pnpm`으로 스캐폴딩했다. CI(`pnpm/action-setup`)와 Vercel 모두 `pnpm-lock.yaml`로 자동 인식한다.

### D-11. 접근 게이트는 Next 미들웨어 basic auth

Vercel Deployment Protection 대신 `src/proxy.ts`에서 basic auth를 구현한다.

**이유**: Vercel의 비밀번호 보호는 유료 플랜 기능이고, 무료 플랜의 Vercel Authentication은 계정 소유자만 들어갈 수 있어 남에게 보여줄 수 없다. 미들웨어 방식은 무료이고 자격증명을 공유할 수 있다.
**설계**: `GATE_USER`/`GATE_PASSWORD`가 비어 있으면 **통과가 아니라 503으로 차단**한다(fail closed). 설정 누락이 게이트 해제로 이어지면 안 된다. 개발 환경만 예외로 통과시킨다.
**제거 시점**: 로드맵 `7.7`.

### D-12. Supabase는 로컬 스택 + 클라우드 병행

`supabase init` + `supabase start`로 로컬 Docker 스택을 쓰고, 마이그레이션을 로컬에서 검증한 뒤 클라우드에 push한다.

**이유**: RLS 정책(D-02)은 실험 횟수가 많고 되돌리기가 잦다. 실제 프로젝트에 직접 실험하면 `1.1a`와 `7.6a`의 반복 비용이 커진다.

### D-13. `[locale]` 재배치는 Phase 0이 아니라 4.0에서

D-08의 `/[locale]/articles/[slug]` 구조를 Phase 0에서 미리 만들지 않고 `src/app/`을 평면으로 둔다.

**이유**: next-intl 없이 `[locale]` 세그먼트만 만들면 라우팅이 깨진다. Phase 1의 기사 목록(1.12)은 영문 UI라 평면 경로로 충분하고, 4.0에서 파일 몇 개를 옮기는 비용이 더 싸다.

### D-14. 커밋 메시지에 Claude 표기를 넣지 않는다

`Co-Authored-By: Claude ...` 트레일러와 `🤖 Generated with ...` 문구를 쓰지 않는다. 커밋은 `feat(0.2): ...` 처럼 로드맵 태스크 번호로 시작한다. `CLAUDE.md` §4에 규칙으로 반영했다.

### D-16. RSS 피드 선정 기준 (실제 목록은 1.5)

- **3~5개**, 7개 카테고리를 모두 커버. 카테고리당 최소 1개 경로가 있어야 한다

- **1차 출처 성격의 피드(기관·저널 발표)와 종합 과학·기술 매체를 섞는다.** 전자만 쓰면 산업·정책이 비고, 후자만 쓰면 Tier 1 확보(3.10)가 어려워진다

### D-17. Node 22 LTS 를 쓴다

`.nvmrc` = 22, `package.json` engines `>=22.0.0`, CI 는 `node-version-file: .nvmrc`.

**이유**: `@supabase/supabase-js` 가 Node 20 이하를 지원 중단 예정이라고 경고하고,
실제로 **Node 20 에서는 서비스 클라이언트 생성이 실패한다** — "native WebSocket not found".
Node 20 은 `WebSocket` 이 `--experimental-websocket` 플래그 뒤에 있고 22 부터 기본 제공된다.
`ws` 폴리필로 덮을 수도 있지만 지원 중단을 미루는 것뿐이고, Vercel·Trigger.dev·GitHub Actions
모두 Node 22 를 지원한다.

**주의**: Next.js 서버(`@supabase/ssr`)는 Node 20 에서도 동작했다. 실패하는 건 파이프라인이
쓰는 `createServiceClient` 쪽이다. 로컬에서 `nvm use` 를 빠뜨리면 파이프라인 테스트만 깨진다.

**Node 버전을 정하는 곳이 세 군데다.** `.nvmrc` 는 로컬과 CI 만 커버한다.
Trigger.dev 클라우드 런타임은 `trigger.config.ts` 의 `runtime` 이 정하며,
기본값 `'node'` 는 Node 20 이다. 처음에 `.nvmrc` 만 올렸다가 **로컬·CI 는 전부 통과하는데
배포된 파이프라인만 죽는** 상황을 겪었다. `runtime: 'node-22'` 로 맞췄고,
`tests/runtime-version.test.ts` 가 `.nvmrc` / `engines` / `runtime` 세 값의 일치를 지킨다.

### D-18. 권한을 대시보드 토글이 아니라 마이그레이션에 박는다

Supabase 프로젝트 설정:

| 항목 | 값 |
|---|---|
| Enable Data API | ON (supabase-js 를 쓰므로 필수) |
| Automatically expose new tables | **OFF** |
| Enable automatic RLS | ON |

다만 **이 토글에 보안을 의존하지 않는다.** 로컬 스택에는 같은 토글이 없어서
로컬과 운영이 갈라지고, 그런 차이는 운영에서만 터진다. 같은 효과를
`20260905040000_explicit_grants.sql` 에 넣어 양쪽이 동일하게 동작하게 했다:

- `revoke all ... from anon, authenticated` 후 필요한 것만 `grant`
- `alter default privileges ... revoke all` — 새 테이블은 기본적으로 권한 없음
- `CREATE TABLE` 이벤트 트리거로 새 테이블에 RLS 강제

**왜 기본 grant 로는 부족했나**: Supabase 기본값은 anon 에게 `TRUNCATE` 와
`REFERENCES` 까지 준다. **TRUNCATE 는 RLS 로 걸러지지 않는다** — PostgREST 가
그 동작을 노출하지 않을 뿐이다. `revoke insert, update, delete` 만으로는 남는다.

**권한 모델**: RLS 정책이 "어느 행"을, grant 가 "어느 동작"을 정한다. 둘 다
통과해야 접근된다. 새 테이블을 추가하면 explicit_grants 마이그레이션에
grant 를 더해야 앱에서 보인다 — 잊으면 노출이 아니라 미표시로 실패한다.

최종 권한:

| 테이블 | anon | authenticated |
|---|---|---|
| articles / article_sources / article_translations | select | select |
| profiles | — | select, update |
| scraps | — | select, insert, delete |
| monthly_summaries | — | select |
| seen_feed_items / source_texts / pipeline_runs | — | — |

`scraps` 에 update 를 주지 않은 것은 의도적이다. 수정할 필드가 없다.

**service_role 도 명시적으로 부여해야 한다** (`20260905050000_service_role_grants.sql`).
처음에는 anon/authenticated 만 다루고 service_role 은 Supabase 기본값에 기댔는데,
"Automatically expose new tables" 를 끈 클라우드에서는 service_role 도 아무 권한을
받지 못한다. 로컬 라이브 테스트는 전부 통과하는데 배포된 파이프라인만
`permission denied for table pipeline_runs` 로 죽었다.

service_role 은 RLS 를 우회하지만(BYPASSRLS) **테이블 grant 는 따로 필요하다.**
anon/authenticated 와 달리 화이트리스트로 관리하지 않고 `grant all on all tables`
+ default privileges 로 준다. 파이프라인은 모든 테이블에 접근해야 한다.

### D-19. 재채점 대상을 밴드가 아니라 순위로 고른다

기획서 §2.1 의 "임계선 ±2 안의 토픽을 재채점"을 **"1차 점수 상위 9개(상한×3)를 재채점"**으로 바꾼다.

**이유**: 밴드는 대상 수가 점수 분포에 따라 요동친다. 실측에서 총점 중앙값이 9인데
임계값이 10이라 밴드가 134개 중 **72개**를 삼켰고, 재채점만 월 $8.21 이 나왔다.
그룹핑+채점 합계($3.85)보다 크다. 고정비 $12.06 을 예산 $20 에서 빼면 기사당
**8.8센트**만 남아 파이프라인이 예산 안에서 돌지 않는다.

**핵심 관찰**: 상한이 3인 이상 실제로 판단이 필요한 건 상위 몇 개뿐이다.
20등 토픽의 점수가 9인지 10인지는 아무 결과도 바꾸지 않는데 밴드 방식은 거기에도 돈을 쓴다.

**효과**: 월 $8.21 → $1.02. 비용이 분포와 무관하게 고정되어, 뉴스가 몰리는 날에도
폭증하지 않는다.

**감수하는 것**: 1차 채점이 크게 틀려서 15등 토픽이 사실 1등감이었다면 놓친다.
다만 1차 채점도 제목과 설명은 봤으므로, 15등이라는 건 그 정보로는 평범해 보였다는 뜻이다.
상위 N 을 상한의 3배로 둔 것은 재채점이 점수를 낮출 수 있기 때문이다.

**연관**: "임계값 통과 48개"는 비용 문제가 아니었다. 조사·작성·번역·이미지는
상한 3개에만 돌므로 변동비가 같다. 하루 기사 수를 임계값으로 조절할지는
별개 질문이며 `2.8` 에서 일주일치 실측으로 정한다.

### D-20. Brave Search 실측 (3.2a)

응답 헤더 실측:

```
x-ratelimit-policy    50;w=1, 0;w=2592000
x-ratelimit-limit     50, 0
x-ratelimit-remaining 47, 0
```

**초당 50회**다. 월 단위 창(2592000초 = 30일)의 값이 `0` 인데, 요청이 정상
처리되므로 "제한 없음"으로 읽는 게 맞아 보인다 — 다만 헤더만으로는 단정할 수
없으니 월 사용량이 늘면 대시보드에서 확인할 것.

**예상 사용량은 하루 9회**(선정 토픽 3개 × 쿼리 3개), 월 270회. 어느 쪽으로
읽어도 여유가 크다.

클라이언트의 호출 간격은 **1.1초로 유지**한다. 초당 50회가 가능해도 우리
사용량에서는 속도가 문제되지 않고, 한도를 건드려 차단당하는 쪽이 훨씬 비싸다.

**tier 필터 실측**: 검색 15건 → 채택 8건(Tier 1 이 7건), 제외 7건
(blocked 2, unknown 4, duplicate-host 1). `.gov`/`.edu` 접미사 규칙이
nih.gov·harvard.edu·princeton.edu 를 잡아 Tier 1 확보(3.10)에 크게 기여한다.
mashable·dailygalaxy·spacedaily 는 `unknown` 으로 제외됐다 — 검증되지 않은
도메인을 쓰지 않는 규칙이 의도대로 동작한다.

### D-21. 출처 도메인 목록의 커버리지 편향과 대응 (3.5 실측)

실제 토픽 3개로 조사 단계를 돌린 결과:

| 토픽 | 결과 |
|---|---|
| Roman 우주망원경 L2 도달 | 출처 5건 (T1 2, T2 3) ✅ |
| 초파리 커넥톰 완성 | 출처 5건, **전부 Tier 1** (biorxiv, eLife, NIH, MRC-LMB) ✅ |
| AD109 수면무호흡 신약 | 출처 1건 → `too-few-sources` 로 skip |

**발견 1 — 도메인 목록이 물리·우주에 치우쳐 있다.** 세 번째 토픽에서 검색 결과
20건이 전부 `unknown` 으로 걸러졌는데, 그중에는 제조사 자체 발표(`apnimed.com`),
학술 출판 플랫폼(`academic.oup.com`), DOI 리졸버, 전문 학회(`aasm.org`,
`thoracic.org`) 처럼 **명백한 1차 출처**가 있었다. 목록이 작성자가 아는 범위를
그대로 반영한 결과다.

→ 출판 플랫폼·DOI·전문 학회·보도자료 배포 서비스를 추가했다.
**추측으로 더 늘리지 않는다.** 조사 단계가 `unknown` 으로 버린 호스트를 남기므로,
3.17 품질 리뷰에서 실제 데이터를 보고 근거와 함께 넓힌다.

**발견 2 — 도메인 확장 후에도 이 토픽은 여전히 실패한다.** 남은 결과가
`duplicate-host` 6건(같은 배포 서비스의 여러 릴리스)이라 매체당 1건 규칙에 걸렸다.
이 토픽은 제조사 발표만 있고 논문도 주요 언론 보도도 없다 — **근거 있는 기사를
쓸 출처 기반이 실제로 없다.** skip 이 올바른 동작이다 (기획서 §2.2).

**발견 3 — 파이프라인이 다음 순위 토픽으로 넘어갈 수 있어야 한다.**
조사는 정상적으로 실패할 수 있다. 상위 3개가 모두 실패하면 4등 토픽이 멀쩡한데도
그날 기사가 0건이 된다. `3.12`/`3.15` 에서 조사 실패 시 다음 순위로 내려가는
경로를 만든다.

### D-23. 문장 길이는 지시만으로 지켜지지 않는다 (3.6)

스타일 가이드가 평균 20단어를 요구하는데 초안 실측은 **평균 38.2단어**였다.
프롬프트에 규칙을 적는 것만으로는 지켜지지 않았다.

| 조치 | 평균 문장 길이 |
|---|---|
| 규칙만 명시 | 38.2단어 |
| + 분할 전/후 예시 | 27.7단어 |
| + 반환 직전 체크리스트 | **22.0단어** |

**교훈 두 가지**:

1. **측정을 반쪽만 하면 잘못된 결론에 이른다.** 처음에는 "30단어 초과 문장 16개"만
   세고 평균을 안 봤다. 그래서 "규칙이 비현실적"이라고 판단해 상한을 40으로
   완화했는데, 실제로는 평균이 38이라 규칙이 아니라 준수가 문제였다.
2. **긴 문장의 원인은 기관명과 소속을 본문에 끼워 넣는 것이다.** 프롬프트에
   구체적인 분할 예시(41단어 → 12+16단어)를 넣으니 크게 줄었고,
   반환 직전 체크리스트가 나머지를 잡았다.

### D-24. 클레임 추출은 출처를 읽지 않는다 — Haiku 로 되돌림

D-06 은 출처 본문을 읽는 단계를 네 개(작성·추출·검증·재작성)로 보고 전부 Sonnet 으로
묶었다. **추출은 출처를 읽지 않는다** — 기사만 보고 검증 가능한 진술을 뽑는 작업이다.
전제가 틀렸다.

되돌린 이유 두 가지:

1. **비용.** 출처 없이 기사(1,200 토큰)만 보내면 Haiku 로 $0.004 다.
   Sonnet + 캐시 읽기로는 $0.011 이 든다.
2. **방법론.** 추출이 출처를 먼저 보면 "출처에 있는 것만 진술로 뽑는" 편향이 생겨
   검증이 자기충족적이 된다. 눈을 가리고 뽑는 편이 옳다.

출처를 읽는 단계는 이제 셋이다: 작성 · 검증 · 재작성. 캐시는 그대로 공유된다.

### D-27. 모델이 지킬 수 있는 지시와 없는 지시

|---|---|

| 단어 수 | 718 | **1047** | 1863 | 600~900 — 너무 짧았다 |
| Flesch Reading Ease | 37.8 | 40.7 | 45.3 | — |
| Flesch-Kincaid 학년 | 11.8 | 12.7 | 14.1 | — |

**뒤집힌 것들**:

1. **실제 기사는 62단어짜리 문장을 예사로 쓴다.** 내가 금지했던 것이 정상이었다.
   긴 문장은 전체의 5.7% 정도로 섞여 있을 뿐이다
2. **분산이 핵심이다.** 실제 기사의 문장 길이 표준편차가 11.6 이다. 긴 설명 문장 뒤에
   짧은 문장을 붙이는 것이 좋은 글의 형태이고, **균일하게 긴 글이 가장 읽기 나쁘다.**
   나는 평균만 보느라 이 축을 아예 놓쳤다
3. **분량 목표가 너무 짧았다.** 실제는 중앙값 1,047단어다
4. Flesch-Kincaid 12.7 — 실제 과학 저널리즘은 "쉬운 글"이 아니다. 고등학교 졸업 수준이다

**코퍼스 구성 규칙**: 우리 저비용 필터(2.1)를 기준 코퍼스에도 적용한다.
처음에는 적용하지 않아 IEEE 회원 소식(FRE 6)과 Quanta 라이브 블로그(11,194단어)가
섞여 들어왔다. **우리가 발행하지 않을 글을 기준으로 삼으면 비교가 성립하지 않는다.**
분량 상한(4,000단어)도 같은 이유로 둔다.

**저장**: 원문은 `.gitignore`, 계산된 지표만 `fixtures/reference/metrics.json` 으로 커밋한다.
제3자 기사 전문을 저장소에 재배포하지 않으면서 대역은 버전 관리된다.

### D-30. 품질 판단은 여러 축으로 본다

지표 하나(문장 길이)를 목표로 삼았다가 프롬프트를 네 번 고치며 성공률을 5/5 → 2/5 로
떨어뜨리고 비용을 57% 올렸다. 대리 지표를 직접 최적화하면 목표가 뒤바뀐다 —
설명을 넣으면 문장이 길어지므로 이해 가능성과 문장 길이는 실제로 반대로 당긴다.

평가는 세 층으로 한다:

1. **계산 지표** (`src/pipeline/write/quality-metrics.ts`) — 문장·어휘·난이도·구조·위반.
   비용 0, 재현 가능. 기준 대역과 대본다
2. **루브릭 판정** (`src/pipeline/write/judge-article.ts`) — Haiku 가 다섯 축을 1~5로
   매기되 **점수마다 근거 문장을 인용하게 한다.** 점수만 있으면 어느 문장을 고칠지 모른다.
   별도로 "일반 독자가 다시 읽어야 할 문장" 목록을 뽑아 판정기가 틀렸는지 사람이
   바로 확인할 수 있게 한다. 개발 전용이고 파이프라인에 넣지 않는다
3. **사람** — `3.17` 품질 리뷰와 D-28 의 독자 투표

**리포트에 합격/불합격을 찍지 않는다.** 대역 밖은 "실제 매체와 다르다"는 뜻이지
"나쁘다"가 아니다.

**생성물을 JSON 으로 저장한다** (`out/articles.json`). 평가할 때마다 기사를 다시
생성하면 비용도 들고 LLM 비결정성 때문에 같은 대상을 평가하는 것도 아니게 된다 —
내가 네 번 튜닝하며 매번 다른 기사를 비교한 것이 판단이 흔들린 이유 중 하나다.

### D-31. "정의가 아니라 설명" — 첫 평가 결과와 프롬프트 수정

평가 프레임워크를 처음 돌리자 계산 지표와 루브릭이 **서로를 검증했다**:

| fixture | 종합 | 이해 | 용어 | FRE |
|---|---|---|---|---|
| fly-connectome | 4.6 | 4 | 4 | 33 |
| lz-dark-matter | 4.4 | 4 | 4 | 34 |
| magic-angle-graphene | 3.2 | 2 | 2 | 21 |
| hall-effect | 3.0 | 2 | 2 | 20 |

Flesch 33~34 는 이해도 4점, 20~21 은 2점. 서로 다른 방식으로 잰 두 지표가 같은
결론을 내므로 둘 다 근거로 쓸 수 있다.

**판정기가 짚은 원인**: 모델이 "쓰기 전에 소개하라"를 **수행하고 있었다.** 다만
정의가 또 다른 낯선 용어로 되어 있었다 —
`the Néel vector, which points along the direction of the alternating atomic magnetic
moments`. 정의는 있지만 "교대하는 원자 자기 모멘트"가 용어만큼 낯설다.

**수정**: 규칙을 "정의가 존재하는가"에서 **"정의가 무엇으로 만들어졌는가"**로 바꿨다.

- 설명 안의 모든 단어는 독자가 이미 가진 것이거나 앞에서 푼 것이어야 한다
- 판정 기준: 이 분야를 처음 보는 독자가 그 설명으로 **그림을 그릴 수 있는가**
- 낯선 개념 두 개를 쌓지 않는다
- 문장 길이를 의도적으로 섞는다 (D-29 의 분산 발견을 프롬프트에 반영)

**수정 후 재측정**:

| fixture | 종합 | 이해 | 용어 | FRE | 걸리는 문장 |
|---|---|---|---|---|---|
| fly-connectome | 4.6 | 4 | 4→**5** | 33→**43** | 3→**2** |
| lz-dark-matter | 4.4 | 4 | 4 | 34→**40** | 3→**2** |
| roman-telescope-l2 | 실패→**4.4** | 4 | 4 | **41** | 2 |
| hall-effect | 3.0→**3.8** | 2→**3** | 2→**3** | 20→**24** | 4 |

**Flesch 가 기준 대역(37.8~45.3) 안으로 들어왔다** — 네 편 중 세 편. 이전에는 0편이었다.
분산도 대역 안으로 들어왔다 (lz 9.4→14.2).

**남은 문제**: hall-effect 는 FRE 24 로 여전히 대역 밖이다. 전문용어가 조밀한
물리 주제는 다른 주제보다 일관되게 어렵다. 이것이 프롬프트로 더 좁혀질 문제인지,
주제 자체의 성질인지는 표본을 더 봐야 안다.

**문장 평균은 네 편 모두 대역 위(27~33 vs 18.7~26.0)로 남아 있다.** 다만 FRE 와
루브릭이 개선됐으므로 문장 길이 자체를 더 쫓지 않는다 — 그것이 D-30 에서
경계한 대리 지표 최적화다.

### D-32. 사람 품질 리뷰 1차 — 막히는 지점은 문장 길이가 아니라 개념 밀도다

기사 4편(`out/read.md`)을 읽고 판정기의 stall point 와 대조했다. **프롬프트는 고치지 않았다.**

**읽기 어려운 기사는 하나였다** — `hall-effect-no-field` (FRE 23.6, 기준 대역 37.8~45.3). 나머지 셋은 대역 안이었다. 판정기가 뽑은 걸리는 문장들의 공통점은 길이가 아니라 **한 문장 안에서 새 개념이 둘 이상 겹치는 것**이었다:

> "In an antiferromagnet the opposing atomic magnets line up along a shared axis called the Neel vector, and whether a zero-field Hall signal is allowed depends on which direction that axis points relative to the crystal's structure."

Neel vector 의 정의와, 그 방향이 물리 효과를 "허용" 하는지가 한 문장에 붙어 있다. 정의를 붙든 채로 대칭성 논증을 따라가야 한다. 문장을 짧게 잘라도 이 문제는 남는다.

**그런데 프롬프트를 고치지 않았다.** 근거가 기사 한 편이기 때문이다. D-27 에서 정확히 이 실수를 했다 — fixture 하나를 보고 프롬프트를 바꿔 성공률을 5/5 에서 2/5 로 떨어뜨렸다. "개념 밀도" 규칙을 넣는 것이 옳을 수 있지만, 그 판단에는 **어려운 주제 여러 편**이 필요하다. 지금 표본은 응집물질물리 한 편이고, 주제가 어려운 것인지 프롬프트가 무너진 것인지 구분할 수 없다.

**다음에 볼 것**: 발행이 쌓이면 FRE 가 대역 아래인 기사를 모아 주제 분야와 대조한다. 특정 분야에 몰리면 주제 난이도이고, 흩어져 있으면 프롬프트다.

**Phase 3 완료 조건과의 차이**: 조건은 "연속 발행된 기사 10개" 였는데 실제로 읽은 것은 fixture 기반 4편이다. 10편을 채우려면 새 토픽 조사가 필요했고(편당 $0.12~0.22), 4편에서 이미 한 방향이 보여 더 쓰지 않기로 했다. 발행이 쌓이는 대로 `2.8` 주간 캘리브레이션에서 다시 본다.


### D-33. 번역은 자식 태스크 안에서, 재시도는 다음 런의 스윕으로

한국어 번역을 **`build-article` 자식 태스크 안**에서 돌린다. 발행 배치(07:00)가 아니다.
실패하면 기사는 `ready_pending` 으로 남고, **다음 일간 런의 시작에서 스윕**
(`src/pipeline/fill-assets.ts` 의 `sweepPendingAssets`)이 다시 시도한다.

**왜 발행 배치가 아닌가**: D-04 가 01:00 파이프라인과 07:00 발행을 분리한 이유가
장애 격리다. 발행이 LLM 호출을 하기 시작하면 번역 장애가 곧 발행 장애가 된다.
발행은 상태 전이만 한다.

**왜 스윕이 따로 필요한가**: 일간 런은 어제의 토픽을 다시 보지 않는다
(`seen_feed_items` 가 `processed` 다). 기사 쪽에서 훑지 않으면 "다음 런에서 재시도"
(기획서 §2.3)가 성립하지 않고, 기사는 2일 뒤 `failed` 로 조용히 사라진다.
스윕은 기사 생성 **앞**에 둔다 — 어제 것이 오늘 아침 발행에 맞춰져야 하고,
오늘 작업이 어디서 막히든 어제 것은 이미 끝나 있어야 한다.

Phase 5 의 커버 이미지도 같은 자리에 붙는다. 자산이 하나 늘 뿐 구조는 같다.

**미번역 검출**: 구조 검증(4.3a)만으로는 모델이 영문을 그대로 돌려주는 실패를
못 잡는다 — 섹션 수도 출처 배열도 완벽히 일치하고 내용만 번역되지 않은 채 통과한다.
본문의 **한글 비율**(기본 0.5, `TECHNOW_MIN_HANGUL_RATIO`)을 함께 본다.
고유명사와 용어 병기는 영문으로 남는 것이 정상이라 100% 를 요구할 수 없다.

**비용**: 실측 기사당 $0.046 (Sonnet). 하루 3편이면 월 $4.1 이 더해진다.
D-07 의 월 $20 예산은 Phase 3 실측만으로도 이미 $24.4 로 넘겨 있었다 —
Phase 4 는 이것을 해결하지 않는다. `pnpm cost:report` 로 실측이 쌓이면 다시 본다.

### D-34. 언어 리다이렉트는 쿠키를 보고, 307 로 낸다

`/` 처럼 언어 없는 경로는 `proxy.ts` 가 `NEXT_LOCALE` 쿠키 → `Accept-Language` →
`en` 순으로 골라 리다이렉트한다. D-08 은 `profiles.locale` 을 기본값이라고 했지만
**요청마다 DB 를 조회하지 않는다** — 프로필이 원본이고 쿠키가 사본이다.
언어를 바꿀 때와 로그인할 때 쿠키를 프로필에 맞춘다. 로그인하지 않은 독자도
선택이 유지되어야 하므로 쿠키가 맞는 자리이기도 하다.

**307 이지 308 이 아니다.** 목적지가 쿠키에 따라 달라지므로 영구 리다이렉트로 내면
브라우저가 그것을 캐시해, 언어를 바꿔도 `/` 가 계속 옛 언어로 간다.
실제로 308 로 만들었다가 브라우저에서 그 증상을 보고 잡았다.

next-intl 의 미들웨어는 쓰지 않는다. `proxy.ts` 에 이미 basic auth 와 Supabase 세션
갱신이 있고, 셋을 한 응답에 합치는 것보다 접두사가 없을 때만 리다이렉트하는
순수 함수 하나가 단순하고 테스트된다.

### D-35. 번역이 없는 기사는 그 언어에서 보이지 않는다

`/ko` 의 목록과 상세는 `article_translations` 에 행이 있는 기사만 보여준다.
번역이 없으면 목록에 없고 상세는 404 다. 영어 본문으로 대체하지 않는다.

**이유**: 언어를 바꿨는데 내용이 안 바뀌는 것은 반쪽 상태다 (CLAUDE.md §5).
4.6 이후 새 기사는 번역 없이 발행되지 않으므로, 이 조건에 걸리는 것은
Phase 4 이전에 발행된 기사뿐이고 시간이 지나면 사라진다.
`hreflang` 도 실제로 있는 언어만 가리킨다 — 없는 언어판을 알리면 검색엔진이 404 를 받는다.

### D-36. 월 예산을 $20 → $25 로 올린다. 그래도 하루 3편은 안 맞는다

사용자 판단으로 `budget.monthlyUsd` 를 25 로 올렸다 (2026-09-05).

**그런데 산수가 여전히 맞지 않는다.** 실측(표본 1런) 기준:

| 항목 | 실측 | 월 환산 (30일) |
|---|---|---|
| 고정비 (발굴~선정) | $0.16 / 일 | $4.8 |
| 변동비 — 조사·작성·검증 | $0.218 / 편 | |
| 변동비 — 한국어 번역 | $0.046 / 편 | |
| 변동비 합 | **$0.264 / 편** | 하루 3편이면 $23.8 |
| **합계** | | **$28.6** |

$25 예산으로도 하루 3편은 넘는다. 하루 **2편**이면 $20.6 으로 들어온다.

**아무것도 자동으로 막지 않는다.** `projectMonthlyCost` 는 경보만 울리고
(`shouldAlert`, 기본 비율 0.8), 실제 상한은 호출 지점 카운터가 건다 (CLAUDE.md §2.6).
표본이 1런이라 지금 `dailyCap` 을 건드리지 않는다 — 실측이 쌓인 뒤 셋 중 하나를 고른다:

1. `TECHNOW_DAILY_CAP` 을 2 로 (재배포 없이 env 로 바뀐다)
2. 예산을 더 올린다
3. 편당 단가를 낮춘다 — 재작성 비율(D-31)과 조사 페이지 수가 후보다

`budget.variableUsdPerArticle` 목표(0.2)는 **실측에 맞춰 올리지 않았다.**
목표를 실측으로 갱신하면 그 값이 신호이기를 그만둔다.

### D-37. 커버 이미지는 Flux schnell. 비교 대상은 Imagen 이 아니라 Recraft 였다

**Imagen 4 Fast 는 부를 수 없었다.** 기획서 §7 이 대안으로 지목했지만 이 fal 계정에서
`fal-ai/imagen4/*` 는 어떤 경로로도 404 다 ("Application imagen4 not found", 2026-09-06 실측).
그래서 실제로 부를 수 있는 모델 중 플랫 일러스트에 가장 강하다는 **Recraft V3**
(장당 $0.04, Flux 의 13배)로 같은 4편을 돌렸다.

**Recraft 는 실격이다.** 품질이 낮아서가 아니라 **글자를 그려 넣기 때문이다.**
화면 가득 엉터리 단어가 박혔다 — "Corlolbedie Estrimacre comoal", "Mrretmtz", "0-222 - 8M".
프롬프트에 `No text, no letters, no numbers` 를 넣었는데도 그렇다.
덤으로 `flat vector, no 3D render` 도 무시하고 정밀 아이소메트릭 렌더를 냈고,
지하 제논 검출기 기사에 **인공위성**을 그렸다.

가짜 글자가 박힌 커버는 없느니만 못하다. 13배를 더 내고 못 쓰는 결과를 받는다.

**Flux schnell 로 확정한다.** 싸서가 아니라 지시를 지키는 유일한 후보라서다.

**남은 한계 — 추상적 주제에서 색면으로 도망간다.** 4편 중 2편이 그랬다:

| 기사 | 결과 |
|---|---|
| 초파리 커넥톰 | 초파리를 그렸다. 쓸 만하다 |
| 로만 우주망원경 | 망원경을 그렸다. 쓸 만하다 |
| 암흑물질 검출기 | 색면 두 개. 주제가 없다 |
| 반강자성 홀 효과 | 색면과 육각형. 주제가 없다 |

**사물이 있는 기사는 그리고, 개념뿐인 기사는 못 그린다.** 프롬프트를 한 번 고쳐
(배경색 못 박기, "negative space" 제거, "Draw the single object" 로 끝맺기)
팔레트 이탈은 잡았지만 이 경계는 그대로였다. D-27 과 같은 교훈이다 —
한 번의 프롬프트 수정으로 모델 능력의 경계를 옮길 수는 없다.

**대응은 5.4 의 hold-back 이 이미 한다**: 커버가 필수 자산이 되면 실패한 기사는
발행되지 않는다. 다만 "색면만 있는 이미지" 는 생성 실패가 아니라 성공이라
코드가 잡지 못한다. 발행이 쌓인 뒤 사람이 보고 판단한다 (`5.6` 이후).
카테고리별로 구체적 사물을 힌트로 주는 방법이 후보다.

### D-38. 커버는 개념을 그리지 않는다 — 그릴 장면을 먼저 고른다

D-37 이 남긴 문제: **사물이 있는 기사는 그리고 개념뿐인 기사는 색면으로 도망간다.**

원인은 모델이 아니라 시킨 일이었다. 기사 제목·요약을 이미지 모델에 그대로 넘기고
"이 이야기의 중심 사물을 그려라" 고 했는데, 개념 기사에는 중심 사물이 없다.
이미지 모델은 기사를 읽지 않았고 비유를 고를 수 없다.

**개념을 그대로 그려낼 필요가 없다.** 좋은 기사 그림은 셋 중 하나다 (사용자 정리):

| 유형 | 무엇을 그리나 | 언제 |
|---|---|---|
| `subject` | 주제 자체. 한눈에 보이는 사물·기기·생물 | 가능하면 항상 이것 |
| `scene` | 상황을 설명하는 비유적 장면. 사물이 아니어도 된다 | 볼 것이 없을 때 |
| `future` | 이 연구가 통했을 때의 일상 | 결과의 값이 가능성에 있을 때 |

그래서 **단계를 하나 넣었다**: 기사를 읽은 Claude(Sonnet)가 위 셋 중 하나로
장면을 정하고, Flux 는 그것을 렌더링만 한다
(`src/prompts/cover-concept.ts`, `src/pipeline/illustrate/choose-concept.ts`).

**프롬프트를 더 조이는 방향이 아니다.** D-27 과 D-37 이 그 실패를 두 번 적고 있다 —
프롬프트 수정으로 모델 능력의 경계는 옮겨지지 않는다. 판단이 필요한 자리에는
판단하는 단계를 놓는다.

**실측 (같은 fixture 4편, 2026-09-06)**

| 기사 | 전 (D-37) | 후 | 고른 유형 |
|---|---|---|---|
| 암흑물질 검출기 | 색면 두 개 | 암반 동굴에 매달린 제논 탱크, 안에서 한 번의 섬광 | `subject` |
| 반강자성 홀 효과 | 색면과 육각형 | 자석이 없는 슬래브에서 전류가 옆으로 휘는 장면 | `scene` |
| 초파리 커넥톰 | 초파리 (양호) | 초파리 + 몸을 따라 빛나는 신경망 | `subject` |
| 로만 우주망원경 | **지상** 망원경 (틀림) | 지구를 배경으로 한 우주망원경 | `subject` |

4/4 에 볼 것이 생겼다 (전 2/4). 홀 효과에서 `scene` 을 고르고 "자석이 프레임에
없는" 장면을 잡은 것이 이 구조의 값을 보여준다 — 기사의 요지가 "자기장 없이
나타나는 홀 효과" 이고, 그것은 사물이 아니라 상황이다.

**사람은 얼굴만 금지한다.** 실존 인물 위험은 얼굴에서 온다 (CLAUDE.md §5).
실루엣·뒷모습·얼굴 아래 상체는 허용한다 — `future` 유형을 사람 없이 그리기는 어렵다.

**글자는 계속 전면 금지.** 글자를 100% 정확히 쓰는 모델이 아직 없다 (D-37 의 Recraft).
장면 선택 단계에도 "글자가 필요한 장면은 고르지 말라" 를 넣었다 — 표지판·화면 글씨·
그래프 축 라벨이 필요한 아이디어는 애초에 버린다.

**입력 범위**: 기획서 §2.4 는 "제목과 한 줄 요약" 이라고 적었지만, 장면 선택은
**섹션 소제목과 각 섹션 첫 문장**까지 읽는다. "무엇이 달라지나" 섹션이 없으면
비유와 미래 장면을 고를 근거가 없다. 본문 전체는 싣지 않는다.

**비용**: 장면 선택 기사당 약 $0.006 (Sonnet). 이미지 $0.003 을 더해 커버 하나에
$0.009 — 하루 3편이면 월 $0.8 이다. D-36 의 예산 문제는 여전히 Claude 쪽이다.

**남은 것**: 화풍의 일관성이 완벽하지는 않다 (한 장은 회색 띠가 크고, 한 장은
위쪽에 흰 줄이 있다). 발행이 쌓인 뒤 `mode` 별로 결과를 세어 보고 판단한다 —
지금 표본은 4편이고, 여기서 프롬프트를 또 만지면 D-27 을 세 번째로 반복하는 것이다.

### D-39. 커버의 alt 는 비운다. 그리고 next/image 는 사설 IP 를 막는다

**`alt=""`** — 커버는 장식이다. 그림이 전하는 정보는 바로 옆의 제목과 요약에 이미 있고,
우리는 생성된 그림의 설명을 DB 에 저장하지 않는다. 지어낸 alt 를 넣으면 화면낭독기
사용자에게 **틀린 설명**을 읽어주게 된다. 장면 설명(D-38 의 `scene`)을 저장해
alt 로 쓰는 것은 나중에 볼 수 있지만, 그때도 "그림에 실제로 그려진 것" 과
"그리라고 시킨 것" 은 다르다.

**Next 16 의 이미지 최적화는 사설 IP 를 거부한다** (SSRF 방어). 로컬 Supabase 는
`127.0.0.1:54321` 이라 여기 걸려 400 이 났다. `images.dangerouslyAllowLocalIP` 를
**개발 환경에서만** 켠다 — 프로덕션 Storage 는 공개 https 호스트라 필요가 없고,
켜둔 채로 배포하면 우리 서버가 내부망 이미지를 대신 가져다 주는 통로가 된다.

`remotePatterns` 는 `NEXT_PUBLIC_SUPABASE_URL` 에서 호스트를 읽어 `covers` 버킷
경로만 연다. 호스트를 상수로 박으면 환경이 바뀔 때 이미지가 조용히 깨진다.

### D-40. 월간 요약은 모델이 문장만 쓰고 구조는 코드가 만든다

카테고리로 묶고, 순서를 정하고, 링크를 거는 것은 코드다. 모델은
도입 한두 문장, 카테고리마다 한 문장, 기사마다 두세 문장만 쓴다.

**이유**: 카테고리는 이미 DB 에 있고 슬러그도 우리가 안다. 모델에게 구조까지
시키면 잘못 분류된 기사와 빠진 기사가 생기고, 그것을 검증하는 코드를 또 써야 한다.
D-38 (커버 장면 선택)과 같은 판단이다 — **판단이 필요한 자리에만 모델을 쓴다.**

설명이 빠진 기사는 그 기사의 한 줄 요약으로 채운다. 사용자가 직접 담아둔 기사가
요약에서 말없이 사라지면 사라진 줄도 모른다.

**렌더링**: 요약은 마크다운 한 덩어리로 저장된다 (`monthly_summaries.summary_text`).
범용 마크다운 라이브러리를 넣지 않고 우리가 만드는 부분집합만 렌더한다
(`## 소제목`, `- [제목](슬러그) — 설명`, 문단). 라이브러리를 넣으면 우리가 쓰지도 않는
문법 — 이미지, 원시 HTML, 임의 URL — 까지 해석하게 되고, 그것은 저장된 텍스트가
화면에서 무엇이든 될 수 있다는 뜻이다. **링크 목적지도 본문에서 받지 않는다**:
슬러그를 기사 경로로 조립할 뿐이다.

**100건 이상은 카테고리별로 나눠 부른다** (기획서 §2.6). 한 번에 보내면 뒤쪽 기사의
설명이 성의없어진다 — 채점에서 청크를 20개로 자른 것과 같은 이유다.
나눠 부르면 도입이 여러 개 나오므로 첫 묶음의 것만 쓴다.

**비용**: 사용자당 $0.005~0.011 (Sonnet). 스크랩이 없는 달에는 모델을 부르지 않는다.

### D-41. 스크랩 폴더는 번역이 없어도 기사를 숨기지 않는다

D-35 는 `/ko` 목록에서 번역 없는 기사를 숨긴다고 정했다. **스크랩 폴더와 월간 요약은
그 반대다** — 번역이 없으면 원문 제목으로 보여준다.

**이유**: 목록에서 안 보이는 기사는 독자가 존재를 몰랐던 기사다. 스크랩 폴더에서
안 보이는 기사는 **자기가 담아둔 것이 사라진 것**이고, 사라진 이유를 알 방법이 없다.
같은 규칙을 두 곳에 적용하면 한쪽이 반드시 틀린다.

### D-42. 로컬과 클라우드의 인증 설정이 달랐다 — 배포본에서 가입·로그인 불가

**증상**: 배포본에서 회원가입과 로그인이 되지 않았다. 로컬에서는 잘 됐다.

**원인**: `supabase/config.toml` 의 `enable_confirmations = false` 는 **로컬 스택에만**
적용된다. 클라우드 프로젝트는 기본값인 이메일 확인 **켜짐**(`mailer_autoconfirm: false`)
이었다. 그래서 배포본에서는

- 가입 → 사용자는 생기지만 **세션이 없다** → 우리 코드가 `/` 로 보내 로그아웃 화면이 나온다
- 로그인 → `Email not confirmed`

**조치 (2026-09-06)**: 공개 전까지는 클라우드에서도 확인을 끈다. 사이트가 Phase 7 까지
basic auth 뒤에 있어 확인 메일이 지금 보호하는 것이 없다.

**코드 쪽 버그도 함께 고쳤다**: `signUp` 이 세션 없는 응답을 성공처럼 다뤄
말없이 `/` 로 보냈다. 이제 "메일을 확인하세요" 를 돌려준다 — 오류가 아니라 안내이므로
빨간 글씨가 아닌 별도 상태로 표시한다.

**남은 것 (7.x)**: 공개 전에 확인을 다시 켜려면 두 가지가 필요하다.
1. **인증 콜백 라우트가 없다.** 확인 메일의 링크는 `redirect_to` 로 돌아오는데
   그 코드를 세션으로 바꾸는 라우트가 우리 앱에 없다. 비밀번호 재설정도 같은 경로를 쓴다
2. **SMTP 공급자.** Supabase 기본 메일은 시간당 2~3통 제한이라 실사용에 못 쓴다

**교훈**: `config.toml` 은 로컬 전용이다. 클라우드 설정과 어긋나면 **로컬에서만 되는 기능**이
생기고, 배포하고 나서야 안다. 인증처럼 환경마다 설정이 갈리는 것은 배포 후 실제로
눌러봐야 한다 — 이번에도 사용자가 눌러보고 알았다.

### D-43. 알림은 일부러 실패하는 태스크로 보낸다

Trigger.dev 의 내장 알림은 **태스크 실행 실패**에 걸린다. 그런데 우리가 알려야 할
조건 대부분은 예외가 아니다 — 예산 80% 초과도, "기사 2건이 hold-back 끝에 failed" 도
런이 성공한 상태에서 일어난다.

그래서 `alert` 태스크를 두고, 알릴 일이 생기면 그것을 띄우고 던진다
(`src/trigger/alert.ts`). 판단은 순수 함수에 있고(`src/pipeline/alerts.ts`)
전달만 태스크가 한다 — CLAUDE.md §3 대로 Trigger.dev 없이 테스트된다.

**왜 런 자체를 실패시키지 않나**: 그러면 재시도 로직과 로그가 거짓말을 한다.
성공한 런을 실패로 표시하면 "실패한 런" 이라는 신호가 무의미해지고,
`pipeline_runs.status` 도 틀리게 된다.

**대가**: 대시보드에 실패한 실행이 쌓인다. 그것이 알림 기록이기도 하다.
외부 모니터링(Sentry 등)을 붙이지 않은 이유는 지금 규모에 과하고,
공급자가 하나 늘면 그것도 관리 대상이 되기 때문이다.

**사용자가 해야 할 것**: Trigger.dev 대시보드에서 알림(이메일 또는 Slack)을 켜야
실제로 전달된다. 코드만으로는 로그에만 남는다.

### D-44. Rate limit 카운터는 DB 에, 판정은 security definer 함수에

Vercel 서버리스는 인스턴스가 계속 바뀐다. 메모리 카운터는 아무것도 막지 못한다.
공급자를 늘리지 않고 이미 쓰는 Postgres 에 고정 윈도우 카운터를 둔다
(`rate_limits`, `check_rate_limit`).

**앱은 테이블에 접근하지 못한다.** anon 에게 준 것은 함수 실행 권한뿐이다.
자기 카운터를 지울 수 있으면 상한이 아니다.

**고정 윈도우를 쓰는 이유**: 요청자당 행이 하나로 유지된다. 슬라이딩 윈도우는
요청마다 행이 쌓이고 그만큼 정리 부담이 커진다. 경계에서 두 배까지 통과할 수 있지만,
목적이 남용을 늦추는 것이라 그 정도 오차는 감수한다.

**판정에 실패하면 통과시킨다.** DB 가 잠깐 흔들렸다고 로그인을 막으면 장애가 두 배가
된다. rate limit 은 남용을 늦추는 장치이지 인증이 아니다.

실측 (로컬): `auth` 상한 10 에서 11번째부터 차단, 다른 IP·다른 버킷은 영향 없음,
anon 의 테이블 직접 접근은 `permission denied`.

### D-45. 아카이브의 달은 PT 기준이다. 메인은 기간으로 자르지 않는다

**문제**: 목록 상한이 30 이고 페이지네이션이 없어서, 하루 3건이면 **열흘 뒤부터

### D-46. 하루 상한 3 → 5, 예산 $25 → $40. 카테고리별 매일 발행은 채택하지 않는다

2026-09-06. 사용자 요구는 "매일 각 분야별로 한 편 이상" 이었다. 카테고리는 7종(D-15)
이므로 하루 최소 7편이 된다. **세 가지 이유로 채택하지 않았다.**

**1. 비용.** 실측 편당 $0.3625 × 7편 × 30일 + 고정비 = **월 $79.4.** 예산 $25 의 3.2배다.
재시도를 0으로 만들고 번역·커버를 그대로 두는 이론적 최저치로도 월 $40.7 이다.

감안하면 7편에 약 12시도가 필요한데 자격을 갖춘 토픽이 8건뿐이다. 임계값을 낮추면
채점기가 "중요하지 않다" 고 판단한 주제로 기사를 쓰게 된다.

**3. 파이프라인에 카테고리 개념이 없다.** 카테고리는 `write-article.ts` 의 출력 스키마

지금 코드로는 분야별 할당을 강제할 방법이 자체가 없다. 게다가 피드 150건 중 90건이
phys.org·ScienceDaily(물리·우주·바이오)라 `industry-policy`·`robotics-hardware` 는
후보가 0건인 날이 생긴다 — 코드로 지킬 수 없는 약속이 된다.

**대신 상한만 3 → 5 로 올렸다.** 5는 도달 목표가 아니라 천장이다. 위의 공급 제약 때문에
실제 편수는 3~5 사이에서 움직이고, 월 비용은 $35~$54 사이에 앉는다.

예산은 $25 → **$40**. 다만 **예산만 올리는 결정이 아니다** — 편당 단가를
$0.3625 → $0.27 로 내리는 작업(D-47)이 같이 간다. `variableUsdPerArticle` 은
0.2 → 0.24 로 (0.24 × 5 × 30 = $36 + 고정비 $2.7 = $38.7 ≤ $40).

`rescoreTopN` 도 9 → 15 로 같이 올렸다. "상한의 3배" 규칙(D-19)을 유지한 것이고,
공급 병목을 조금 넓히는 효과도 있다. **이 연동을 놓치면 후보가 상한보다 적어져
조용히 공급이 막힌다** — `tests/config.test.ts` 가 이 관계를 강제한다.

**테스트에서 배운 것**: 예산 리터럴을 기대값에 박아둔 테스트 3개가 깨졌다
(`alerts.test.ts`, `cost-projection.test.ts`). 예산은 이미 두 번 바뀌었다(D-36, 여기).
경보가 검사하는 것은 "예산 대비" 이지 특정 금액이 아니므로 `budget.monthlyUsd` 에서
유도하도록 고쳤다.

### D-47. 비용의 레버는 재시도를 싸게 만드는 것이 아니라 1회 통과율이다

2026-09-06. 예산 초과의 원인을 실측으로 추적한 결과다.

| 사실 | 근거 |
|---|---|
| 변동비의 78% 가 작성+검증 | fixture 실측 $0.1691 × 5시도 = $0.85 / $1.0876 |
| 출력 토큰이 변동비의 68% | 프로덕션 런 (output 74,261 토큰) |
| 1회 통과 $0.108~$0.131, 재시도 건 $0.177~$0.218 | fixture 5건 |

**전부 1회에 통과하면 편당 $0.21, 월 $20.8 로 예산 안이다. 초과분은 전액 재시도
비용이다.**

**먼저 틀린 가설**: 재시도를 싸게 만들면 된다고 보고 "지적된 문장만 고치는" 경로를
구현해 A/B 했다. 결과는 **가설 불성립** — 통과율 3/5 로 동일, 비용은 6% 더 비쌌다.
구현 결함이 원인이다: 고친 기사 **전체**를 돌려받으므로 출력 토큰이 줄지 않고,
프롬프트에 기사 본문이 추가되어 입력만 늘었다. (표본 5건이라 통과율 차이를 볼
검정력도 없었다 — 그래서 fixture 를 12건으로 늘린다.)

**실패한 진술을 실제로 들여다본 결과, 검증기는 옳게 작동하고 있었다:**

```
✗ "Hubble's mirror weighs more than a quarter of 186 kilograms"
  → 출처는 "Roman 의 거울이 Hubble 의 1/4 미만" 이라고 했다 (부등식을 뒤집은 산수)
✗ "AA stacking regions where the two layers ..."
  → 출처는 AA stacking 을 언급만 했다 (출처가 이름만 댄 것을 설명으로 확장)
```

둘 다 **작성자의 과잉 주장**이지 검증기의 과잉 엄격이 아니다. 따라서 손댈 곳은
검증기가 아니라 **작성 프롬프트**다. 그리고 "출처를 넘어서지 않게 쓰기" 는 품질
향상과 같은 방향이므로, **비용 인하와 품질 향상이 상충하지 않는다.**

**부수 발견 — 단어 수 지시는 죽은 글자였다.** 프롬프트는 `Aim for 600 to 900 words`
인데 실제 출력은 917·1078·1178 단어였다. 그런데 그 출력이 오히려 기준 코퍼스
(실제 과학 매체 15편)의 중앙값 1047 단어에 맞는다. 지시대로 600~900 이 됐다면
기준 대역에서 멀어졌을 것이다. D-27("모델은 생성하면서 세지 않는다")이 예측한 대로다.
이미 지켜지고 있는 구조 지시(3~5 섹션 × 1~3 문단 × 3~5 문장 = 9~75 문장)가
기준 대역의 문장 수(p25 28.5 ~ p75 70.5)를 그대로 만든다. **작동하는 지시가 있으므로
작동하지 않는 지시를 지운다.**

비용 절감을 위해 기사를 짧게 만들지는 않는다 — 기준 대역에서 멀어진다.

### D-51 후속. 신선도 판정을 tier 통과분으로 좁힌 것은 오판이었다

2026-09-06, 필터를 넣은 첫 프로덕션 런에서 **유일한 후보가 오탐으로 버려졌다.**

```
"Social isolation in childhood linked to NEET status in young adults"
  → research-failed: stale-topic (출처 0건)
```

직접 검색해보니 **5일 전 보도가 있었다** (`theconversation.com`). 그 도메인이
tier 목록에 없어 판정 모집단에서 빠졌고, 남은 tier 통과분(pubmed 41일,
cambridge 40일, mdpi 1064일)만 보니 오래된 토픽으로 읽혔다.

원래 근거는 "버릴 도메인의 날짜는 신호가 아니다" 였는데 **틀렸다.**
tier 는 "이 도메인을 출처로 인용할 것인가" 이고 신선도는 "이 토픽이 지금
뉴스인가" 다 — **다른 질문이다.** 인용하지 않을 매체가 5일 전에 다뤘다는 사실은
그 토픽이 최근 소식이라는 증거이지 그 매체를 쓰겠다는 뜻이 아니다.

**검색 결과 전체로 판정하도록 고쳤다.** 두 필터를 곱하면 교집합이 좁아져
멀쩡한 토픽이 사라진다. 실제 사례를 회귀 테스트로 박았다.

**교훈**: 새 필터는 첫 런에서 무엇을 잡았는지 반드시 들여다본다. 이 건은 잡은
것이 1건뿐이라 눈에 띄었지만, 여러 건을 잡았다면 "필터가 일하는구나" 로
읽고 넘어갔을 것이다.

---

**채점기에 날짜를 넘겨 novelty 축이 판단하게 하는 방안은 채택하지 않았다.**
결정적으로 배제할 수 있는 것을 LLM 판단에 맡기면 비싸고 불안정하다 (CLAUDE.md §2.6).

**곁가지로 `feeds:live` 스크립트 버그를 고쳤다.** 파일 인자가 빠져 있어서
`pnpm feeds:live` 가 **라이브 테스트 전체**를 돌리고 있었다. 피드만 보려다
Claude·Brave·fal 호출이 전부 나갔다.

### D-50. 표시용 라벨이 기사를 죽였다. 검증기가 깨지면 검증을 다시 건다

2026-09-06. 프로덕션 런(`run_06g7i930rc7bi2i4b247i1jj01`)에서 기사 한 편이
이렇게 사라졌다:

```
verify-error — 클레임 추출 실패: Failed to parse structured output:
  claims.2.kind: Invalid option: expected one of
  "number"|"name"|"date"|"causal"|"attribution"
```

**두 가지가 겹친 사고다.**

**1. `claim.kind` 는 아무 판정도 태우지 않는데 enum 이었다.**

사용처를 세어보니 딱 한 곳, 대조 프롬프트의 표시용 라벨이다
(`buildVerifyPrompt` 의 `[0] (number) ...`). 그런데 모델이 목록 밖의 값을
하나 내놓자 zod 가 응답 **전체**를 거부했고, 완성된 기사가 통째로 버려졌다.

`z.string()` 으로 풀고 다섯 개 목록은 `.describe()` 지시로 남겼다. 모델은 여전히
그 중에서 고르려 하고, 빗나가도 파이프라인이 멈추지 않을 뿐이다.

**실패해도 되는 것과 안 되는 것을 구분한다.** 근거 판정은 엄격해야 하지만
(CLAUDE.md §2.5) 라벨은 아니다. 스키마 엄격성을 일률적으로 적용한 것이 실수였다.

**2. 검증기가 깨졌는데 작성자를 벌하고 있었다.**

`buildArticle` 은 `verification.error` 에도 루프를 계속 돌았다. `unsupported` 가
비어 있어 `repairable` 이 false 라, **기사를 처음부터 다시 썼다.** 깨진 것은
검증기이고 기사는 멀쩡했는데 Sonnet 작성 호출을 한 번 더 지불하고 그 기사를 버렸다.

`verifyWithRetry` 를 추가했다 — **같은 기사로 검증만 다시 건다** (2회).
`translateWithRetry` 와 같은 모양이다.

- **`error` 일 때만 재시도한다.** 근거 실패(`passed === false`)는 사고가 아니라
  판정이므로 다시 걸지 않는다
- 재검증도 깨지면 `continue` 가 아니라 `break` 다. 기사를 다시 써도 검증기가
  고쳐지지 않는다. 검증하지 못한 기사는 내보내지 않는다 (§2.5)

`tests/pipeline/build-article.test.ts` 에 호출 횟수로 고정했다 — 작성이 두 번
불리면 테스트가 깨진다.

### 같은 런에서 확인된 것들

- **`build_failure`/`build_detail` 기록이 정상 동작한다.** D-49 의 마이그레이션

- 월 추정 **$36.34** (예산 $40, 91%). `shouldAlert: true`
- 편당 변동비 $0.575 — fixture 의 $0.1912 와 3배 차이인데 분모가 다르다.
  fixture 는 작성+검증만이고 여기는 조사·번역·커버가 다 들어간다.

### D-52. 커버를 사진 품질로 바꾸고, AI 생성임을 표기한다

2026-09-06. 사용자가 커버 품질 향상을 요청했고 **완전한 사진 품질**과
**이미지 예산 월 $8** 을 택했다.

**베이크오프** (`pnpm covers:bakeoff`, 실제 기사 5건 × 4모델, $0.475):
Flux Pro v1.1 Ultra 가 확연히 앞섰다. 격차가 가장 큰 곳은 **추상 주제**였다 —
단백질 구조 예측, 플라스마 제어처럼 평면 벡터 화풍이 색면을 내던 유형(D-37)에서
Ultra 는 무너지지 않았다. schnell → Ultra 로 바꾼다.

**D-38 을 뒤집는 결정이다.** D-38 은 사진 화풍을 일부러 피했다: "사진처럼 보이는
이미지는 실제 사건의 사진으로 오해된다 — 우리 기사에는 실제 사진이 없다."
그 위험을 사용자에게 제기했고 사용자가 사진 품질을 택했다.
**위험이 사라진 것이 아니므로 표기로 상쇄한다.**

| | |
|---|---|
| 기사 페이지 | `<figcaption>` 으로 "AI로 생성한 이미지입니다" |
| 목록 카드 | 이미지 우하단 `AI` 배지 + `sr-only` 전체 문구 |

`src/components/cover-image.tsx` 하나로 묶었다. 두 곳이 같은 `<Image fill>` 블록을
복붙하고 있었고, 표기를 각각 넣으면 **한쪽만 고쳐지는 날이 온다.** 이미지와 표기가
한 덩어리여야 그럴 수 없다. `tests/cover-image.test.tsx` 가 두 variant 모두에서
표기가 나오는지 고정한다.

`alt` 는 계속 비운다. 커버는 장식이고 생성된 그림의 설명을 저장하지 않으므로
지어낸 alt 는 틀린 설명이 된다. **장식 이미지에 대한 고지는 이미지 설명과 다른 것이라**
캡션과 `sr-only` 가 맡는다.

**화풍이 바뀌어도 유지하는 것** (CLAUDE.md §5 — 화풍의 문제가 아니다):
글자 없음, 얼굴 없음, 로고 없음. 특히 **사진 화풍에서 얼굴 위험은 오히려 커진다** —
평면 벡터의 어설픈 얼굴은 아무도 닮지 않지만 사진의 그럴듯한 얼굴은 실존 인물처럼 읽힌다.

사진 화풍에서 새로 넣은 것: **연출된 정물·매크로·구조 사진**으로 못 박고
기자회견장·사고 현장 재현을 금지했다. "이것이 그 현장 사진" 오해를 프롬프트 단계에서 막는다.

### D-52 후속. 사진 → 시네마틱 3D 렌더 (같은 날 두 번째 전환)

사진 화풍으로 프로덕션 런을 한 번 돌려 커버 5장을 함께 보고 방향을 다시 잡았다.

**사물이 주인공인 주제는 잘 나왔다** (위성·엔진·분자·DNA). **풍경이 주제이면
다큐멘터리 사진으로 무너졌다** — 조류인플루엔자 기사에서 갈라진 뻘·창고·새 떼가
나왔고 실제 취재 사진과 구분되지 않았다. 프리픽스에 `no news scene`,
`no reconstruction of a real event` 를 넣었는데도 그랬다.

사용자가 고른 방향은 **가장 잘 나온 두 장을 닮게** 하는 것이었다 — 초파리 커넥톰의
발광 네트워크, DNA 가닥의 3D 렌더. 둘 다 "사진일 리 없는" 이미지였다.

**핵심 교훈: 부정형 지시를 긍정형으로 바꿨다.**

```
안 통함  'No ... news scene, no reconstruction of a real event.'
통함     'Unmistakably a computer-generated render: luminous, slightly
          heightened, more vivid than reality. Never looks like a photograph.'
```

사진 화풍일 때도 부정형 금지는 이미 있었고 지켜지지 않았다. "~하지 마" 는 무엇을
하라는 말이 아니라서 모델이 채울 자리가 남는다. D-27 의 교훈("지시는 압력이지
보장이 아니다")과 같은 계열이지만 방향이 다르다 — **금지가 아니라 대체를 준다.**

같은 가뭄 주제로 검증했다 (`puerto-rico-drought`):

| | 사진 화풍 | 3D 렌더 화풍 |
|---|---|---|
| 결과 | 갈라진 뻘·창고·새 떼 | 발광하는 균열 + 와이어프레임 물통 |
| 취재 사진 오해 | 높음 | 없음 |

**부수 효과: 목록 통일감이 처음으로 생겼다.** 사진 화풍에서는 저조도 지시를
넣었는데도 밝은 배경(엔진)이 나와 목록에서 한 장만 튀었다. 렌더 화풍에서는
어두운 배경 + 앰버 발광이라는 한 가지 언어로 4장이 묶인다.

**이것이 D-38 의 우려를 구조적으로 해결한다.** 사진처럼 보이지 않으면 실제 사건의
사진으로 오해될 일이 없다. 표기(카드 배지·기사 캡션)는 그대로 두지만 **이제
표기가 유일한 방어선이 아니다** — 표기는 마지막 방어선이지 첫 번째가 아니다.

**남은 관찰**: 4장 중 1장(가뭄)에 위아래 검은 레터박스 띠가 생겼다.
`Cinematic` 이라는 단어 때문으로 보인다. 16:9 카드에서 잘리지만 화면을 낭비한다.
재발하면 그 단어를 뺀다.
